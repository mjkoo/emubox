## Context

See proposal.md for motivation. What shapes the approach:

- `modules/kiosk` today: `users.users.player` (home `/data/home/player`, groups `video input audio`), SDDM with `wayland.enable`, `autoLogin = { enable = true; user = "player"; }` (`relogin` unset, so nixpkgs' default `false`), `defaultSession = "emubox"`, a `wayland-sessions/emubox.desktop` whose `Exec` is `emubox-session` (a `writeShellApplication` looping `cage -- es-de --force-kiosk` with `ESDE_APPDATA_DIR=/data/es-de`, `|| true`, `sleep 2`, and `TODO(design 4/9/11)` comments), and the polkit rule granting `player` `org.freedesktop.login1.power-off` and `reboot` plus their `-multiple-sessions` variants. `/data/es-de`, `/data/roms`, `/data/media` exist from `modules/library`'s tmpfiles rules, owned `player`.
- ES-DE 3.4.1 (verified in the source the package builds): `ESDE_APPDATA_DIR` is honoured; settings live at `<appdata>/settings/es_settings.xml` as a flat document of `<string|bool|int name="..." value="..." />` elements that ES-DE rewrites on exit; custom systems at `<appdata>/custom_systems/es_systems.xml` complement the bundled file. Relevant defaults: `UIMode=full`, `UIMode_passkey=uuddlrlrba`, `Theme=linear-es-de` (bundled with `modern-es-de` and `slate-es-de`), `ApplicationLanguage=automatic`, `ShowQuitMenu=false`. `GuiMenu.cpp` adds the QUIT entry only when `!ForceKiosk && UIMode != "kiosk"`, since upstream commit `defb16b6` (2020-12-17); `openQuitMenu()` builds rows for Quit ES-DE, Reboot, Power off and Suspend, each behind a confirmation, and power off runs `shutdown --poweroff now`. RetroPie's EmulationStation keeps a Quit menu holding only "shutdown system" in kiosk mode; Batocera's shows QUIT in every mode.
- SDDM 0.21.0 `Display::start`: autologin runs when `(daemonApp->first || Autologin.Relogin) && Autologin.User != ""`, otherwise the greeter is started. So with `Relogin=false` the first display of the daemon's life autologins and every later one shows the greeter. nixpkgs orders `display-manager.service` after `plymouth-quit.service`; the greeter compositor in Wayland mode is Weston by default.
- disko's install test (`lib/tests.nix`, `create_test_machine`) starts the installed VM with a hard-coded `-m 1024` and no memory option, which is why the base layer forces SDDM off there. A plain `runNixOSTest` node over `nixosModules.emubox` evaluates to a driver (checked on 2026-08-30) with: the package set built at the call site with the host's config and overlay; `boot.initrd.systemd.services.{rollback-root,persist-dirs,persist-machine-id}.enable = false`; `fileSystems."/persist"` and `"/data"` as tmpfs with `neededForBoot`; the test sops file and key forced as the install test does; `services.openssh.enable` forced off; `virtualisation.memorySize = 2048`; `virtualisation.qemu.options = [ "-vga none -device virtio-gpu-pci" ]` (what nixpkgs' `nixos/tests/cage.nix` uses to run cage). `hosts/emubox/facts.nix` supplies the facts.
- Pinned nixpkgs carries `ruff` 0.15.14, `ty` 0.0.38, `python3` 3.13, and `nixfmt-tree` 2.5.0, which accepts `settings` and `runtimeInputs`, so the formatter can gain ruff without replacing `nixfmt-tree`. `writers.writePython3Bin` runs flake8 at build time unless `doCheck = false`.
- cage 0.3.0 from nixpkgs has XWayland on its PATH and gives focus to the newest window.

## Goals / Non-Goals

**Goals:**
- One config-editing program and one convention ("the flake owns these keys") that E4 to E8 extend by adding entries, not mechanisms.
- A failure state the family can recognise (the greeter) and the admin can act on, instead of a black screen or an endless relaunch.
- A VM test that sees the graphical session, so the loop, the counter and the greeter fallback are proven before hardware exists, and a place for every later session-level assertion.

**Non-Goals:**
- `es_systems.xml` content, `retroarch.cfg` and standalone emulator keys: E4 (the editors exist after this change; the key tables are E4's).
- Save redirection and the leak check (E5), `SDL_JOYSTICK_DEVICE` and hotkeys (E6), Skyscraper pass 2 in prepare (E8), `emubox-mode` and the writer of `/run/emubox/mode` (E9). The session script keeps the mode check and a placeholder comment for the leak check.
- Boot time, the TV's native mode, and how the patched menu looks on the real TV: E12.
- Turning `emubox-prepare` into a uv project; it is one stdlib file until it outgrows that.

## Decisions

### D1. SDDM stays the launcher; the loop counts crashes and hands a broken frontend to the greeter

The session stays an SDDM autologin session, as the earlier plan had it, with one change: `services.displayManager.sddm.autoLogin.relogin = false`, replacing that plan's `relogin = true`. The session script owns relaunching: after each `cage -- es-de` exit it measures the run; a run under 60 s increments a counter, a longer one resets it; at three consecutive short runs the script exits non-zero. SDDM then, per its `Display::start` logic, shows the greeter; a reboot restores autologin. A run that exits after more than 60 s (a menu quit, a crash mid-play) relaunches after a 2 s pause. The mode check stays at the top of each iteration.

The script runs under `set -euo pipefail`, so every command whose failure is expected is written to keep `set -e` from ending the session. `ESDE_APPDATA_DIR` is exported once at the top of the script, before the loop, so that both `emubox-prepare` and the frontend read it (D3 owns that contract). `cage -- es-de` is invoked as `if cage -- es-de; then :; fi` (equivalently, its exit status captured with `rc=0; cage -- es-de || rc=$?`) rather than with a trailing `|| true`: the loop needs the run's length, not its status, and a bare `|| true` would also swallow the status the recovery epics may want. `emubox-prepare` is *not* wrapped that way: a non-zero prepare ends the session, and that is deliberate, because prepare's recreate policy (D3) already absorbs every failure the box can actually produce - a missing settings file, a missing parent directory, a document a killed frontend truncated. What is left after that policy is a bug in prepare or an unwritable `/data`, neither of which relaunching three times would fix, and both of which should stop at a greeter the admin can log into rather than loop invisibly.

`EMUBOX_CRASH_WINDOW` (D5) is a test-only hook: the shipped value is the 60 s the kiosk spec states unconditionally, there is no module option for it, and no product behaviour depends on its being settable. The spec's 60 s SHALL stands as written.

The greeter guarantee is scoped to the display manager's lifetime, not the boot's: SDDM's `Relogin=false` keys off `daemonApp->first`, the first display of the *daemon's* life. A restarted `display-manager.service` would autologin again. On this host that path is not automatic - nixpkgs' `display-manager.service` carries no `Restart=`, so systemd does not revive it, and the only way to restart it is an admin running `systemctl restart display-manager` or a `nixos-rebuild switch` that changes the unit. Both are deliberate admin acts and both are a reasonable way to get out of the greeter, so the behaviour is correct; the kiosk spec says "for as long as that display manager keeps running" rather than "for the remainder of the boot" to match.

- Why not a dedicated systemd unit on tty1 in the shape of nixpkgs' `services.cage` (considered and rejected during brainstorming): it would drop SDDM from the kiosk path and give `Restart=` semantics, but at the cost of a PAM stack of our own, a second login path next to the recovery specialisation's SDDM, and a failure state that is a stopped unit and a black screen rather than a greeter. The daemon cost of SDDM is small; the unified path and the visible failure state were judged worth more.
- Why `relogin = false` rather than `true` with a counter: with `Relogin=true` SDDM would log `player` in again the moment the script gives up, so the greeter could never be reached from a crash loop. With `false`, "the script exits" and "the greeter appears" are the same event, and there is nothing to count on SDDM's side.
- Why 60 s and three: a frontend that survived a minute has loaded its theme and gamelists, so a later exit is a quit or a runtime crash, not a startup failure; three short runs distinguish a broken configuration from one bad start. Both are constants in the script, recorded in the module comment; no option, since nothing else varies them.
- `--force-kiosk` is dropped from the launch line: the settings key is asserted by prepare before every launch (D3), and with the flag ES-DE's own unlock flow behaves oddly (the forced mode is temporary and the setting it saves on unlock is not what the next launch sees). The behaviour the spec wants, kiosk at every launch and unlock within a running frontend, is exactly what an asserted `UIMode=kiosk` gives.

### D2. The kiosk quit menu is a patch on the vendored ES-DE

`pkgs/es-de/kiosk-quit-menu.patch` changes two places in `es-app/src/guis/GuiMenu.cpp`: the QUIT entry is added regardless of UI mode, and `openQuitMenu()` skips the "Quit ES-DE" and "Suspend" rows when the effective mode is kiosk (`ForceKiosk` or `UIMode == "kiosk"`), leaving Reboot and Power off with their confirmations. The package's header names upstream commit `defb16b6` as the origin of the hidden menu and describes the patch in one sentence; `patches = [ ./kiosk-quit-menu.patch ]` means a bump to a source where the hunks no longer apply fails in the patch phase, which is the guard the spec asks for. The existing `versionCheckHook` and find-rules grep stay.

- Why a patch rather than ES-DE's idiom of a custom system with power-off scripts, the physical power button, or kid mode: the custom system works and is what the design planned as the "emubox tools" system, but the author chose the native menu; the power button alone leaves nothing on screen; kid mode shows the menu but hides every game not flagged `kidgame`, which fights E8's ingest flow. The patch is a local fork of a deliberate upstream choice, carried on every bump; its size (two hunks) makes that acceptable.
- Power off and reboot go through `shutdown --poweroff now` and its reboot analogue, which reach logind, where the existing polkit rule answers for `player`. No new permission.
- `ShowQuitMenu=true` is one of the owned settings (D3) so the QUIT entry opens the menu rather than the plain "really quit?" box.

### D3. `emubox-prepare`: one Python program, key tables per file, format-preserving editors

`pkgs/emubox-prepare/` holds `emubox_prepare.py`, `test_emubox_prepare.py`, `ruff.toml` and `package.nix`. The program is stdlib-only Python 3.13.

**The invocation contract.** This is the whole of it; D1, D5, D6 and the tasks derive their call sites from here and add nothing to it.

- **argv:** `emubox-prepare <owned-values-json> <custom-systems-path>`, exactly two positional arguments, always both. `<custom-systems-path>` is the empty string when `emubox.kiosk.customSystems` is empty - never an omitted argument, so the call site has one shape and the removal branch is reached by an empty string rather than by `argc`.
- **Environment:** the appdata root comes from `ESDE_APPDATA_DIR`, the same variable ES-DE itself reads (Context). Every path prepare writes - `<appdata>/settings/es_settings.xml`, `<appdata>/custom_systems/es_systems.xml` - is resolved under it. If the variable is unset or empty, prepare writes nothing and exits non-zero with a message on stderr: that is a broken call site, not a broken configuration, so the recreate policy below does not apply to it and the loud failure is what should be seen.
- **Where the variable is set:** `emubox-session` exports `ESDE_APPDATA_DIR` from `emubox.kiosk.appdataDir` (D6) **once at the top of the script, before the loop**, rather than prefixing the `cage -- es-de` line. One export means prepare and the frontend read the same value and cannot drift; a per-command prefix is precisely the shape in which prepare would assert settings into a directory the frontend never reads.
- **Where the binary lives:** `emubox-prepare` joins `environment.systemPackages` alongside `cage` and `es-de` (D6), and that is also how the session script's own call resolves - `writeShellApplication`'s `runtimeInputs` are not used for it, so the session and any outside caller reach one binary on the PAM-exported PATH. `writeShellApplication`'s `runtimeInputs` are script-internal, so without this nothing outside the session - the test driver, or an admin who reached the greeter - can run it.
- **How a caller outside the module obtains the JSON:** the module exposes the rendered file's store path as a readonly internal option (D6) and uses that same value in the session script, so a test interpolates one source of truth rather than scraping the script or re-rendering the JSON and agreeing with itself. The appdata root is exposed the same way and for the same reason, so no caller hard-codes `/data/es-de`.

The program has three parts:

- Editors, one per format, each implementing "read if present, set these keys, write only if changed, create with these keys if absent", and each creating the file's parent directories (mode 0755, owned by `player`, since the session runs as `player`) before writing, because `modules/library`'s tmpfiles rules create `/data/es-de` but neither `settings/` nor `custom_systems/` under it: ES-DE's flat XML (`xml.etree`; the typed elements keyed by `name` are a *rootless forest*, not the children of a single root - `Settings::saveFile` appends them straight to the pugixml document, which `xml.etree` refuses to parse as "junk after document element", so reading wraps the body in a synthetic element and writing drops it again; set-or-append over that list preserves everything else), INI with sections (line-based: comments, order and unknown keys preserved; used by E4's Dolphin, PCSX2, PPSSPP, DuckStation, Azahar files), and RetroArch's flat `key = "value"` file (line-based). Each editor takes a path and a mapping and returns whether it wrote.

  The error policy is recreate, not fail: a file that is missing, unreadable, or malformed (an `xml.etree` `ParseError` on a document a killed frontend truncated mid-write, an INI or RetroArch line that does not parse) is replaced by a fresh file carrying the owned keys, and the program continues. The frontend regenerates everything else it cares about, so the cost of recreating is a lost unowned preference in a file that was already unreadable, while the cost of failing is the family staring at a greeter with no way back. A recreated file is noted on stderr so the journal records it.
- Key tables: a mapping from file to owned keys, computed from arguments the module passes (this change: the ES-DE settings file with `UIMode`, `UIMode_passkey`, `ROMDirectory`, `MediaDirectory`, `Theme`, `ApplicationLanguage`, `ShowQuitMenu` and their types). Later epics extend the table, not the editors.
- The custom systems step: given a non-empty `<custom-systems-path>`, copy it to `<appdata>/custom_systems/es_systems.xml` if it differs, or remove that file when the option is empty. Copy, not symlink: ES-DE and later Skyscraper treat the directory as theirs, and a link into the store would survive a configuration that no longer defines it.

  This step carries the editors' filesystem policy: it creates `custom_systems/` before copying, since tmpfiles creates `/data/es-de` but not that subdirectory, and removal treats an absent target as a no-op rather than an error. The second matters on every shipped box: the default configuration leaves `customSystems` empty with no file present, so the removal branch runs before every launch of the frontend against a path that is not there, and an error would end the session at the greeter.

The module renders the owned values into a JSON file in the store and passes its path as the first argument, so the Python program has no Nix-specific knowledge and its tests run on plain dictionaries. The derivation is `stdenvNoCC.mkDerivation` with `python3` as a build input: `buildPythonApplication` wants a `pyproject.toml` and a fifth file for a program that is one stdlib script. It installs the script as `bin/emubox-prepare` and runs, in `checkPhase`, `ruff check`, `ruff format --check`, `ty check` and `pytest` from `nativeCheckInputs`. `ruff.toml` carries `extend-select = ["ARG"]` and nothing that replaces the defaults. The package is exposed as `checks.${system}.emubox-prepare` for every system the flake evaluates on, so the Mac's `nix flake check` runs the Python checks natively, and the host closure carries the `x86_64-linux` build through the overlay.

- Why not `writers.writePython3Bin`: it runs flake8, which is not the lint this project uses, and it has no place for tests.
- Why not shell with `xmlstarlet`, `crudini` and `sed`: three tools, three quoting disciplines, and no test outside a VM for a component whose whole promise is "touches nothing else".
- Why not generate whole files from Nix: it would overwrite every setting the family or the admin changed in the frontend, which the appliance's configuration model forbids: the flake asserts the keys it owns and leaves every other key as the frontend last wrote it.
- Why not a uv project now: one file and its test need no lock file or virtual environment; the skill's tool choices (ruff, ty, pytest) are applied without its scaffolding. If prepare grows past one file, it becomes a uv project under `pkgs/emubox-prepare/` and the derivation switches to nixpkgs' uv support.

### D4. Formatter and checks in `flake.nix`

- `formatter` becomes `nixfmt-tree.override { runtimeInputs = [ ruff ]; settings.formatter.ruff-format = { command = "ruff"; options = [ "format" ]; includes = [ "*.py" ]; }; }` per system, so `nix fmt` and `nix fmt -- --ci` (what CI and `just fmt-check` run) cover Python. `ruff check` is not a formatter (it would need `--fix` to be one, and the project's checks never mutate); it lives in the package's `checkPhase`.
- `checks.${hostSystem}.kiosk` is `pkgs.testers.runNixOSTest (import ./tests/kiosk.nix { ... })` built from `hostPkgs`, so the node's package set is the host's (config and overlay included) and the node imports `self.nixosModules.emubox` plus `./hosts/emubox/facts.nix` plus the overrides from Context. `checks.${system}.emubox-prepare` is `pkgsFor system` applied to the package for every system.

  The two are merged rather than assigned separately: `flake.nix` today sets `checks.${hostSystem}` from a single `let ... in { ... }`, which would collide with a `forAllSystems` attrset on `x86_64-linux`. `checks` becomes one `forAllSystems` expression whose `x86_64-linux` entry is the per-system `emubox-prepare` attribute merged (`//`) with the host-only checks, so the Linux system carries both and the Mac carries only `emubox-prepare`.

  `pkgsFor` is bare `nixpkgs.legacyPackages.${system}` - no `nixpkgsConfig`, no overlay - so the darwin check reaches the package with `(pkgsFor system).callPackage ./pkgs/emubox-prepare/package.nix { }` directly - the file, not the directory, since `callPackage` on a directory imports a `default.nix` that does not exist here, not by importing `./pkgs` with a darwin `pkgs`. Importing `./pkgs` would appear to work because its Linux-only attributes stay lazy, but it would break the first time something in that file evaluated eagerly; naming the direct `callPackage` keeps the darwin path independent of `pkgs/default.nix`'s contents. The `x86_64-linux` closure still gets the package through the overlay as usual. On that system the check and the package output are deliberately *not* the same store path: `checks.x86_64-linux.emubox-prepare` comes from `pkgsFor`, a bare `legacyPackages` set, while `packages.x86_64-linux.emubox-prepare` comes from `hostPkgs` and is what `cache-roots` pushes, matching the flake's existing principle that a package output is the host's own store path by construction. The two agree in content; only the cached one is the box's.
- The devShell gains `python3`, `ruff`, `ty` and `pytest`, the way it already carries `sops`, `actionlint` and `cachix`: the package's `checkPhase` runs them at build time, but writing the program means running them by hand first, and `nix fmt`'s ruff override covers only formatting.
- `just kiosk-test` builds `checks.x86_64-linux.kiosk`; `just eval` gains its `drvPath`; `just vm-test` is unchanged. README's Development section names the second test and the Python checks.

### D5. The kiosk test

`tests/kiosk.nix` is a `runNixOSTest` argument set: `nodes.machine` with the overrides, `testScript` with these subtests, each mapped to a spec scenario:

- `display-manager.service` active, and autologin proved by the session itself rather than by a process name: `loginctl list-sessions` shows a `player` session on `seat0` and `loginctl show-session <id> -p Active` is `yes`. The greeter's process name is not asserted here - it is the observable the Risks section calls brittle, and an active `player` session on the seat is what "autologin happened" actually means.
- Within 120 s (`wait_until_succeeds`), `pgrep -x es-de` and the parent chain of that PID contains `cage`. 120 s is the test's budget, chosen with headroom for ES-DE starting under llvmpipe; it is not the box's figure, which stays the kiosk spec's 60 s and is an E12 bring-up measurement on real hardware.
- `${nodes.machine.emubox.kiosk.appdataDir}/settings/es_settings.xml` contains each owned key with the declared value (read in Python from `cat`, compared in the driver), including `UIMode_passkey` carrying the test module's non-default passkey, which is what proves the option is wired rather than that ES-DE's own default happens to be there.
- A custom systems file is present with the test module's non-empty `emubox.kiosk.customSystems` (a one-system stub). The empty case is proved on the same node rather than by a second node or a specialisation. The custom-systems path is a store path baked into `emubox-session` at build time, so nothing at runtime can empty it; instead the driver invokes prepare directly on the node while the stub file exists, exactly as D3's contract specifies it: `ESDE_APPDATA_DIR=${nodes.machine.emubox.kiosk.appdataDir} emubox-prepare ${nodes.machine.emubox.kiosk.ownedValuesFile} ""`, run as `player`, with the binary found on the system path (D6) and the JSON's store path read from the module's readonly option rather than scraped from the script. Then it asserts the file is gone. Because the module's empty branch passes exactly that empty second argument (D3), this is the same call the shipped box makes when the option is empty. What it does not prove is that the module *renders* the empty argument, and that is checked outside the VM: task 3.3's `nix eval` of the session script text asserts it. One node, no second closure to build.
This removal subtest runs before any `pkill`: the next loop iteration re-runs prepare with the module's non-empty stub path and would recreate the file, so the ordering is load-bearing rather than incidental.
- Relaunch: with the run already longer than the lowered window (the threshold override below, 10 s), record the frontend's PID, `pkill -x es-de`, `wait_until_fails` on that PID being alive, then `pgrep -x es-de` succeeds within 15 s with a *different* PID. Without the wait and the PID comparison the dying process satisfies the assertion and the subtest passes without a relaunch having happened.
- Greeter: three kills in quick succession, each inside the lowered window, then - after a grace period longer than the loop's 2 s relaunch pause, so that "no frontend" means the loop gave up rather than that it is between iterations - `pgrep es-de` stays empty across repeated checks and `display-manager.service` is still active. That pair is the primary assertion; without the grace period it is momentarily true after any kill and goes green against a counter that never fired. The greeter's process name (`sddm-greeter`, or the greeter's Weston) is a secondary check that may be adjusted or dropped if it proves flaky.
- Reboot restores the kiosk, last of the subtests because the scenario is "rebooted *from the greeter*" and so depends on the three-kill subtest having just run: `machine.reboot()`, then the same waits as the first subtests - display manager active, an active `player` session on `seat0`, `es-de` under `cage` - which proves that ending at the greeter does not outlive the boot.

The threshold override is the one test hook the script carries (`EMUBOX_CRASH_WINDOW`, default 60), set to 10 on the test node through `environment.sessionVariables`, which SDDM's PAM stack exports into the `player` session, so the module needs no knowledge of tests. 10 s answers two opposing constraints: the relaunch subtest needs one run *longer* than the window before its `pkill`, so the driver waits the window out once, and the greeter subtest needs three runs each *shorter* than it, so every kill must land within 10 s of the frontend reappearing. That is comfortable on a node where the frontend returns in seconds after the first cold start, and it is why the window is not the "few seconds" a smaller value would give: at 2 or 3 s the second constraint becomes a race. Both constraints scale with the value, so raising it is safe. It is a test hook only: no module option exposes it, nothing in the product varies it, and the kiosk spec's 60 s stays an unconditional SHALL (D1). The test proves the counter's shape - three consecutive short runs end the session - not its constant.

This table is the change's one enumeration of coverage. Every kiosk-spec scenario has a row; the vm-test delta's assertion list, task 4.2's subtests and the proposal's summary of the check are derived from the "node driver" rows and add nothing to them. When a scenario moves between columns, this table is edited first.

| Kiosk scenario | Proved by |
| --- | --- |
| Frontend up after boot | node driver |
| Frontend data is persistent | `persistence`'s install test (`/data` survives the root wipe); the node shows only that the frontend writes there |
| Kiosk mode at every start | node driver (`UIMode` present with the flake's value) and the editor's unit tests (the drifted-key case is the reassertion after an unlock) |
| Unlock sequence from the configuration | node driver, by proxy: `UIMode_passkey` holds the configured value. That the sequence unlocks is ES-DE's behaviour and needs input synthesis - E12 |
| Power off from the menu | build (D2's patch phase) for the patch applying; the menu on screen is E12 |
| No quit or suspend in kiosk mode | build (D2's patch phase); the menu on screen is E12 |
| First start seeds the file | node driver, and the editor's unit tests (task 1.2) |
| Owned key drifted | editor unit tests (task 1.2) |
| Unowned key preserved | editor unit tests (task 1.2) |
| Settings file unreadable | editor unit tests (task 1.2) |
| Definition present | node driver |
| Definition empty | node driver (the direct `emubox-prepare <json> ""` call), the editor's unit tests, and task 3.3's `nix eval` that the module renders the empty argument |

| Relaunch after exit | node driver |

Two mechanisms carry what the node cannot. The editor's unit tests are why the settings and custom-systems scenarios do not each need a VM boot: they are properties of one Python function against temporary files, and the vm-test delta's second requirement exists to make them a proof rather than an implementation detail. E12 bring-up carries what needs a screen and a person - the quit menu's appearance and the unlock sequence being entered on a controller.

Software rendering under llvmpipe is enough for the assertions the node does make.

### D6. Module surface

`modules/kiosk` gains `options.emubox.kiosk.passkey` (string, default `"uuddlrlrba"`, ES-DE's own) and `options.emubox.kiosk.customSystems` (string, default `""`, the complete contents of an `es_systems.xml`, `<systemList>` wrapper included - the module writes it verbatim and adds no wrapper, which is what the kiosk spec's "holds exactly that definition" and the test's "equals the stub" both require), renders the owned-values JSON and, when `customSystems` is non-empty, the custom systems file with `pkgs.writeText`. What the session script passes to `emubox-prepare` is D3's contract and nothing else: the JSON's path, then the rendered file's path or the empty string when the option is empty - never a store path to an empty file, which would leave the removal branch unreachable. `hosts/emubox` sets no passkey in this change; the default stands until the admin chooses one. The non-default passkey lives only in the kiosk test module (D5), which is where the option's wiring is proved.

Three further pieces of surface come from D3's contract: `options.emubox.kiosk.appdataDir` (path, `readOnly`, `internal`, `/data/es-de`, carrying a comment that `modules/library`'s tmpfiles rule spells the same path and the two must agree; `readOnly` keeps the option itself from drifting) and `options.emubox.kiosk.ownedValuesFile` (path, `readOnly`, `internal`, defaulted to the rendered JSON), so the session script and any test read one value for each, and `emubox-prepare` added to `environment.systemPackages` beside `cage` and `es-de` so it can be run from outside the session. The `TODO(design 4)` comment is replaced by the prepare call; `TODO(design 9)` and `TODO(design 11)` stay as they are.

### D7. What the flake publishes, and how that set stays licence-clean

`cache-roots` is `unfreeCores ++ lib.attrValues vendored`, and this change puts a third kind of thing in it. This decision owns the membership; the packages delta's licence guard, its "On the cache" scenario, `emubox-prepare`'s `meta`, and the sentences task 5.4 sweeps in `flake.nix`, `justfile`, `.github/workflows/ci.yml` and `README.md` are all derived from here.

| Category | Members | Licence posture | Recorded where |
| --- | --- | --- | --- |
| Unfree emulator cores | Whatever the selection in `flake.nix` picks from the RetroArch packages the host installs, narrowed to the cores whose licence is redistributable | Redistributable in the form pushed, enforced by that narrowing rather than asserted | nixpkgs' `meta.license.redistributable` on each core, read by the selection |
| Vendored packages | `es-de` (MIT), `freeimage` (FreeImage Public License or GPL), `duckstation` (CC-BY-NC-ND 4.0, pushed as the upstream AppImage's contents extracted unmodified) | Each recorded in its own `pkgs/<name>/package.nix`; DuckStation's is the one that needed an argument, made there | `pkgs/*/package.nix` |
| The project's own programs | `emubox-prepare`, and whatever later epics add | MIT, the repo's licence, declared in a `LICENSE` file this change adds and in the package's `meta.license` | `LICENSE`, `pkgs/emubox-prepare/package.nix` |

The mechanism differs by how a category gets its members, and that is the point of the table's split:

- The vendored packages and the project's own programs are **curated**: a person adds each one, and settles its posture in the same edit, in that package's own `package.nix`. Nothing needs to inspect them at push time because nothing enters without a human deciding it should.
- The unfree cores are **derived**: the set is whatever the emulators module happens to install, so no human sees a new member arrive, and a curated posture is not available for them. They get a programmatic guard instead. `flake.nix` selects them today with an `isUnfree` predicate reading `meta.license.free`, and `free` is not the field that governs redistribution - nixpkgs carries `redistributable` separately, and the two differ exactly where it matters (`cc-by-nc-nd-40` is `free = false, redistributable = false`, which is why DuckStation needed a written argument at all). The selection therefore narrows to cores whose licence is redistributable. `flake.nix:34`'s own comment already states this invariant - "emulator cores such as libretro-snes9x are unfree-redistributable" - and this change is what makes the code enforce it. A non-redistributable core drops out of the cache and is built by whoever needs it, which is the correct trade.

That split is why the licence guard in the `packages` capability is written over every store path the project publishes rather than over a list of categories: a category added without a posture, or a derived set whose guard reads the wrong field, is the failure this decision exists to prevent, and a guard that enumerates categories cannot catch either.

The guard speaks of every store path the project publishes, and `cachix push` uploads each root's whole closure, not only the roots this table lists. That is deliberate and needs no further mechanism: a closure member is a nixpkgs package whose licence posture is recorded where nixpkgs defines it, which is exactly what the guard's second sentence asks for. This table owns the roots - the paths the project chooses to publish - and the closure follows from them.

- Why MIT for the project's own programs: the repo has carried no `LICENSE` at all, which makes it all-rights-reserved and leaves anyone pulling `emubox-prepare` from the public cache without a grant. MIT matches ES-DE's own licence, imposes nothing on the vendored packages beside it, and makes the guard's claim about this category true rather than merely harmless.
- Why the unfree cores are inside the guard rather than beside it: they are most of what the cache holds and have the widest spread of terms, from "redistributable non-commercially" to "not redistributable at all". A guard whose subject excluded them would govern the smaller half of the problem.

## Risks / Trade-offs

- [ES-DE under llvmpipe on the test node is too slow even for the test's 120 s budget, or cage cannot open the virtio GPU] → nixpkgs' own cage test runs cage on `virtio-gpu-pci`; ES-DE needs OpenGL 3.3, which llvmpipe provides. The wait is already 120 s (D5) against a 60 s box figure, so there is headroom; raising it further is a one-line change in the test and does not touch the spec. If ES-DE needs a resolution the VM does not offer, the virtio GPU is given one: `-device virtio-gpu-pci,xres=...,yres=...` in the `virtualisation.qemu.options` the test module already sets. Like the other mitigations here that is a one-line change inside the test - the launch line stays flagless (D1) and the module gains no option for it.
- [2 GB is not enough for SDDM plus cage plus ES-DE on the test node] → The plain node has a memory knob; raising it is a one-line change. The CI runner has 16 GB.
- [`EMUBOX_CRASH_WINDOW` never reaches the session - `environment.sessionVariables` not exported by SDDM's PAM stack, or the name misspelled] → The script falls back to 60 s and the symptom is remote from the cause: the greeter subtest's third `pkill` finds nothing to kill, or the relaunch subtest's wait passes for the wrong reason. First check of that failure is `systemctl show-environment` and the session's `/proc/<pid>/environ` on the node, before touching the subtests.
- [The lowered `EMUBOX_CRASH_WINDOW` is too tight on a slow runner: a relaunch takes longer than 10 s, so the greeter subtest's three kills cannot all land inside the window] → Both of D5's constraints scale with the value, so raising it is a one-line change in the test module, costing only the seconds the relaunch subtest waits out. It joins the wait time, resolution and memory size as an expected adjustment.
- [The greeter subtest is brittle: Weston's process name, or SDDM's timing] → The assertion is "no `es-de` process and the display manager still active after the third kill plus a grace period", with the greeter process name as a secondary check that is easy to adjust.
- [The patch drifts on an ES-DE bump] → The patch phase fails the build; rebasing two hunks is the cost. The header says where the hunks live.
- [The `ty` check is noisy on stdlib-only code in this ty release] → Rules are downgraded per rule in `ruff.toml`'s sibling `ty.toml` rather than turning warnings-as-errors off, per the project's Python conventions. Skipping the check is not an option: the spec requires the program to be type-checked, so if ty 0.0.38 cannot be made to pass by per-rule downgrades, the task fails and the code or the downgrades change until it does.
- [Prepare runs before every launch of the frontend, each relaunch included, and slows the relaunch] → It reads three small files and writes only on change; milliseconds.
- [The redistributable narrowing (D7) drops a core the cache used to carry, so CI and the box compile it] → The set is the emulators module's unfree cores, and `nix eval` of `cache-roots` before and after the change says exactly which if any (task 3.2). A dropped core costs build time wherever it is needed - CI's runner, and the box itself, which `modules/hardware` already notes builds these paths when it has no cache key - and changes no closure; carrying a non-redistributable binary on a public cache is the cost that is not acceptable.
- [`relogin = false` means a deliberate quit from the full menu (after unlock) also ends at the greeter if it happens three times quickly] → The admin unlocking and quitting three times inside a minute is not a family scenario; a reboot recovers.
- [The install test and the kiosk test both build the host closure] → Same store paths, built once; the second test costs one VM boot.

## Open Questions

None that change the specs, the approach or the tasks.

The main `vm-test` spec's Purpose reads "CI proves what the host configuration guarantees ... through the same boot path the real box uses", which the second test outgrows: the kiosk node does not use the box's boot path. As with the vendored-packages change, the Purpose is reworded directly in `openspec/specs/vm-test/spec.md` on this branch to cover automated proof in a VM and outside one; a Purpose has no delta form, so an in-branch edit is its only shape.

The `packages` Purpose is edited in-branch for the same reason and by the same rule: it enumerates three programs "the pinned nixpkgs no longer carries", a clause `emubox-prepare` does not satisfy, and a Purpose has no delta form. Its new requirement, like vm-test's, reaches the main spec through the delta at archive.

The baseline requirement "The test runs in CI and locally" is a different case: a requirement does have a delta form, so it is generalised through the delta's `## MODIFIED Requirements` block rather than edited in place, and `/opsx:archive` merges it like any other. The generalisation - from the single install test to every VM test the flake defines - makes that requirement the one place enrolment in `nix flake check` and standalone runnability are stated. The kiosk requirement therefore says only what the kiosk test asserts, and the config editor, which is not a VM test, keeps its own cross-system enrolment clause because the KVM-builder condition does not apply to it.
