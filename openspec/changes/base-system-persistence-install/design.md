## Context

See proposal.md for motivation. What shapes the approach:

- The pinned nixpkgs (`nixos-26.05`) enables the systemd initrd by default (`boot.initrd.systemd.enable = true` evaluates on the host today), and it asserts that the script-initrd hooks (`boot.initrd.postDeviceCommands`, `postResumeCommands`) are empty when it is on. The rollback recipe in impermanence's README uses `postResumeCommands`, so it does not evaluate here; the rollback must be a systemd initrd unit.
- The scaffold already declares: the disko layout (`@root @nix @persist @data @cache`, `/persist` and `/data` `neededForBoot`), the impermanence list, `sops.age.sshKeyPaths = [ "/persist/etc/ssh/ssh_host_ed25519_key" ]`, NetworkManager, firewall, PipeWire, systemd-boot with `timeout = 0` and 10 generations, Plymouth, no-sleep, power key, watchdog, zram, fstrim, nix gc/optimise, the `/data` tmpfiles layout, and the `admin` and `player` users. This change fills the `TODO(design 4)` holes and proves the result; it does not restructure modules.
- Options confirmed against the pinned inputs: `networking.networkmanager.ensureProfiles.{profiles,environmentFiles}` (envsubst at service start, output under `/run/NetworkManager/system-connections`), `sops.secrets.<n>.neededForUsers` (decrypts to `/run/secrets-for-users` before the `users` activation step), `sops.templates` and `sops.placeholder`, `services.pipewire.wireplumber.extraConfig` (one attr per `wireplumber.conf.d` fragment; no `extraSettings`/`extraLuaConfig`), `services.journald.extraConfig` (no `settings`), `virtualisation.{useBootLoader,useEFIBoot,useDefaultFilesystems,fileSystems,diskImage}`, and disko's `system.build.installTest` with `disko.tests.{efi,extraConfig,extraChecks,bootCommands}`.
- disko's test harness (`lib/tests.nix`, `testMode = "direct"`) rewrites every `disko.devices.disk.*.device` to `/dev/vdX`, boots an installer VM, formats with the real disko config, installs the real host toplevel with `switch-to-configuration boot`, shuts down, and starts a second VM on the same disks (OVMF when `efi`), then runs `extraChecks`. The nix store is 9p-bound from the host, so the VM never copies the closure.
- The Mac evaluates the flake but builds `x86_64-linux` on a remote builder, an OrbStack NixOS machine. The VM test derivation requires the `kvm` system feature (disko's harness runs QEMU with KVM and the driver's 3600 s global timeout assumes it; under TCG it would not be scheduled, or would time out), and no builder on this desk can offer it: OrbStack has no nested virtualization (its documentation says it is waiting on Apple; unchanged at 2.2.x), and even with it an arm64 guest's `/dev/kvm` accelerates only arm64 guests, so x86_64 KVM does not exist on Apple Silicon at any layer. The nixpkgs vz builder was rejected earlier for unrelated reasons (guest kernel oops). CI is therefore the runner for the VM test in this change: GitHub-hosted `ubuntu-latest` exposes `/dev/kvm`, the workflow's udev step (D8, task 7.2) makes it openable by the build users, and `nix flake check` there builds `checks.x86_64-linux.vm`. Every "run the VM test" in the tasks means a CI run on a pull request from the change branch; the loop is push, wait for the job, read the log. A KVM-capable `x86_64-linux` builder is not a prerequisite and none is planned; one would only shorten that loop. Rejected alternative: driving the same x86_64 nodes from a native aarch64 test driver under TCG on the OrbStack builder (nixpkgs' `hostPkgs` split supports it, disko's `makeDiskoTest` would have to be bypassed and its `qemu_test` replaced), which is a permanent harness for a temporary situation and an emulation-speed unknown against a fixed timeout. What the local builder does cover without KVM, and what is run before every push: `just eval`, the host toplevel, `nix build .#checks.x86_64-linux.vm.driver` (renders, type-checks and lints the test script), and `checks.x86_64-linux.closure-no-secrets`.

## Goals / Non-Goals

**Goals:**
- Land every base-system and persistence behaviour behind a VM test that goes through the boot loader, the initrd and a real btrfs layout, so E3 onward inherit a trustworthy base.
- Keep the module layout of E0; each concern stays in its directory and the persisted list stays a single declaration later epics append to.
- Make the install a one-command procedure whose only admin-held inputs are the age key and the host key.

**Non-Goals:**
- Anything that needs the EQ14 (i915 binding, HDMI audio actually playing, NIC variant, disk id). Those are E12 checklist lines.
- Vendored packages (E2), the kiosk session (E3), backups (E5), the tunnel and push deploy (E10). Their persisted paths and secrets are added by those changes.
- Secure Boot, LUKS, TPM. Not in the design.

## Decisions

### D1. Root rollback is a systemd initrd unit that recreates `@root`

A `boot.initrd.systemd.services.rollback-root` oneshot with `unitConfig.DefaultDependencies = false`, `requires` and `after` on the root partition's device unit (`dev-disk-by\x2dpartlabel-disk\x2dmain\x2droot.device`, derived from `config.fileSystems."/".device` with `utils.escapeSystemdPath`), `after = [ "initrd-root-device.target" ]` as well (the fstab generator hangs that same device on the target for the `/sysroot` entry; systemd 260 `fstab-generator.c`, `add_mount`), `before = [ "sysroot.mount" ]`, `requiredBy = [ "sysroot.mount" ]` (so the root cannot be mounted without it having run), `wantedBy = [ "initrd.target" ]`, `serviceConfig.RemainAfterExit = true` and `unitConfig.ConditionPathIsMountPoint = "!/sysroot"`. The script mounts the btrfs top level (`subvol=/`) from the root partition at a private mountpoint, deletes any subvolumes nested under `@root` (deepest first), deletes `@root`, and runs `btrfs subvolume create @root`, then unmounts.

- Why `RemainAfterExit` (found by the first CI run of the install test, 2026-08-30): a finished oneshot without it is inactive, and nixpkgs' `initrd-nixos-activation.service` runs after `initrd-switch-root.target` with `RequiresMountsFor=/sysroot/run`, which puts a start job on `sysroot.mount` into the switch-root transaction; `sysroot.mount` `Requires=rollback-root.service`, so systemd started the unit a second time, under the mounted root. That run deleted the live `@root`, every mount below `/sysroot` was torn down, and activation failed on a missing `prepare-root`. With `RemainAfterExit` the unit stays active (exited) and the second start job is a no-op. `persist-dirs` and `persist-machine-id` are re-queued the same way through their `requiredBy = initrd-nixos-activation.service` (both finished twice in that run) and get the same setting; their scripts are idempotent, so for them it only removes a duplicate run and a stacked bind mount.
- Why the condition as well: it turns any future re-queue of the wipe while `/sysroot` is mounted into a skipped unit (logged, counted as success by `Requires=`) instead of the deletion of a live root. A wipe that is skipped when it should have run is not silent: the persistence assertions in the VM test see the markers survive.

- Why recreate instead of snapshotting a `root-blank`: a freshly created subvolume is exactly what a blank snapshot is, and it removes an install-time step (creating and never touching the blank snapshot) and a way to get it wrong (the snapshot drifting, or being absent after a disk swap). The install and reinstall procedure gets simpler for free.
- Why not the impermanence README's `old_roots` rotation: it needs `postResumeCommands`, which the systemd initrd rejects, and keeping old roots is disk usage with no consumer here.
- Why not tmpfs root: `/nix` and the rest of the layout are already btrfs; a btrfs root costs nothing and keeps large transient files (journal spool, Plymouth, package downloads) off RAM on a 16 GB box.
- The root partition is addressed as `config.fileSystems."/".device`, which disko sets to the partition label path (`/dev/disk/by-partlabel/disk-main-root`, its default label since the partition has no explicit `name`), the same on the box and in the VM, and a rename in `hosts/` follows through. Both facts the VM run was to verify are settled at evaluation against the pinned inputs: that device path, and `btrfs-progs` in `boot.initrd.systemd.initrdBin` (nixpkgs `tasks/filesystems/btrfs.nix` adds it when `boot.initrd.supportedFilesystems.btrfs`, which the fstab sets), so `boot.initrd.systemd.extraBin.btrfs` is not needed.

### D2. The persisted list is finalized as the scaffold has it, minus the RSA host key

Directories: `/var/lib/nixos`, `/var/lib/systemd`, `/var/lib/bluetooth`, `/var/lib/NetworkManager`, `/var/log`, `/var/lib/emubox`. Files: `/etc/machine-id`, `/etc/ssh/ssh_host_ed25519_key{,.pub}`. `services.openssh.hostKeys` is set to ed25519 only, so no RSA key is generated and the two RSA entries are dropped. Later changes append (cloudflared, restic cache) rather than replace.

`/etc/machine-id` stays in the file list, but the binding is done by an initrd unit in `modules/persistence`, not by impermanence's stage-2 unit. The fallback described below is in force. Impermanence handles files in stage 2 (`persist-<path>.service`, after the root is mounted), and the pinned `mount-file.bash` leaves a target that is already a mount alone, binds a target that is absent or empty, and refuses a target that already has content. What the first boot does was settled from the pinned systemd (260) source rather than left to the VM run: after the initrd's switch-root PID 1 still performs its setup, it detects a first boot whenever `/etc/machine-id` is missing (which a recreated `@root` guarantees on every boot), and a first boot selects `MACHINE_ID_SETUP_FORCE_TRANSIENT`: PID 1 creates `/etc/machine-id` on the ephemeral root with the content `uninitialized` and overmounts a transient id from `/run/machine-id`. Impermanence's stage-2 unit then takes its "already a mount" branch and never populates `/persist`, `systemd-machine-id-commit.service` commits the transient id to the ephemeral root, and the id changes on every boot. So the initrd unit is the mechanism: a oneshot in `boot.initrd.systemd.services` (`DefaultDependencies=false`, `RequiresMountsFor=/sysroot/persist`, `after = [ "sysroot.mount" ]`, `before = [ "initrd-nixos-activation.service" ]`, required by `initrd-nixos-activation.service` so a failed bind stops the boot rather than silently reproducing the changing id, and wanted by `initrd.target`) whose script `mkdir -p`s `/sysroot/persist/etc` and `/sysroot/etc`, touches `/sysroot/persist/etc/machine-id` and `/sysroot/etc/machine-id` if absent, then `mount --bind`s the former over the latter. The bind moves to `/` with the rest of `/sysroot` at switch-root, so stage-2 PID 1 reads the persisted id, or on the box's very first boot finds an empty writable file (which PID 1 does not count as its own "first boot": that flag needs the file missing or reading `uninitialized`), generates an id and writes it in place, which lands on `/persist`. The VM test asserts the id is unchanged across boots and equal to `/persist/etc/machine-id`. Two upstream facts the mechanism leans on: impermanence sets `ConditionFirstBoot=true` on `systemd-machine-id-commit.service` whenever `/etc/machine-id` is in its file list, and that unit would otherwise unmount the bind on every boot; and a `persist-dirs` initrd unit in `modules/persistence` creates every persisted directory under `/sysroot/persist` before impermanence's initrd bind mounts for the neededForBoot ones (`/var/log`, `/var/lib/nixos`), because impermanence creates them only in the activation step those mounts are ordered before, so the first boot after an install would otherwise fail those two mounts and write that boot's uid and gid maps onto the ephemeral root. A service rather than a `boot.initrd.systemd.mounts` entry because a mount unit cannot create its own `what` or its target, and a freshly recreated `@root` has no `/etc`. The VM test's machine-id assertion is what confirms this on a real boot; staging `persist/etc/machine-id` through the D6 `--extra-files` dir remains an install-time nicety, not the mechanism.

### D3. Secrets: one YAML file, templates for env files, `neededForUsers` for the password

- `secrets/secrets.yaml` with keys `wifi_ssid`, `wifi_psk`, `admin_password_hash`; `sops.defaultSopsFile` points at it.
- `sops.secrets.admin_password_hash.neededForUsers = true` and `users.users.admin.hashedPasswordFile = config.sops.secrets.admin_password_hash.path`. This is the only supported way to feed a hash into user creation on a root that is empty at every boot.
- WiFi: `sops.templates."wifi.env".content = "WIFI_SSID=${placeholder.wifi_ssid}\nWIFI_PSK=${placeholder.wifi_psk}"` and `networking.networkmanager.ensureProfiles.environmentFiles = [ config.sops.templates."wifi.env".path ]`. Why a template over a dotenv-format secret: keeps one file in one format; the admin never hand-writes an env file.
- Why the SSID goes through secrets too: it costs nothing to substitute and it keeps the family's network name out of every store path. The spec is silent on where the SSID lives; this design puts it in secrets.
- `.sops.yaml` gets the real admin age recipient (from `~/.config/sops/age/keys.txt`, created with `age-keygen` if absent, the default location sops reads) and the host recipient (`ssh-to-age` on the pre-generated host public key, D6), in a creation rule whose `path_regex` is `secrets/secrets\.yaml$`, not `secrets/.*`: sops uses the first matching rule, and a broad rule would encrypt the test file to the box's recipients. A second creation rule covers `secrets/test\.yaml$`; its recipient is derived from the committed test host key (D7).
- Decryption order: sops-nix's users-stage runs as an activation script before `users`; `/persist` is `neededForBoot` so the host key is present. No sysusers/userborn switch is made.

### D4. WiFi profile via `ensureProfiles`

One profile `family-wifi`: `connection.{id,type=wifi,autoconnect}`, `wifi.{mode=infrastructure,ssid="$WIFI_SSID"}`, `wifi-security.{key-mgmt=wpa-psk,psk="$WIFI_PSK"}`, `ipv4.method=auto`, `ipv6.method=auto`. The generated `.nmconnection` lives on `/run` (tmpfs), so the PSK is never on disk in the clear; `/var/lib/NetworkManager` (leases, seen-bssids) stays persisted. Wired links need no profile: NetworkManager's default DHCP handling covers the install and any later cable.

### D5. Base-system leftovers

- HDMI default sink: `services.pipewire.wireplumber.extraConfig."51-emubox-hdmi-default"` with a `monitor.alsa.rules` entry matching `node.name ~ "alsa_output.pci-.*hdmi.*"` raising `priority.session` to 1500 (ALSA sinks default to 600-1000 and WirePlumber advises not to put a sink above 1500; `priority.driver` is left alone, since it only picks the clock driver and no requirement asks for that), plus `wireplumber.settings."node.restore-default-targets" = false` so a remembered choice can never outrank the rule. WirePlumber has no "default sink by name" setting; priority is the mechanism, and disabling target restore is what makes it declarative.
- journald: `services.journald.extraConfig` with `SystemMaxUse=256M` and `MaxRetentionSec=1month`; storage is persistent because `/var/log` is on the list.
- Everything else in `modules/hardware` stands as scaffolded; the spec now states it so drift is caught.

### D6. Install: host key pre-generated by the admin and injected with `--extra-files`

The admin generates `ssh-keygen -t ed25519 -N "" -f ~/.config/emubox/ssh_host_ed25519_key` once, keeps it with the age key (both outside git, both backed up by the admin), and installs with `nixos-anywhere --flake .#emubox --extra-files <staging dir> root@<box>` where the staging dir holds `persist/etc/ssh/ssh_host_ed25519_key{,.pub}` (0600/0644). disko mounts `@persist` at `/mnt/persist` during install, so the files land on the right subvolume. A `just install <target>` recipe builds the staging dir from the key path and runs the command.

- Why pre-generated over "let the install generate, then re-key": the host identity is then an input, not an output, of the install. A reinstall or disk swap needs no `.sops.yaml` edit, no `sops updatekeys`, and no known_hosts churn, which is the "flake plus one secrets file" property the design asks for. Cost: the admin holds one more small file. Alternative rejected: generate on the box and `ssh-to-age` back, which works once but makes every reinstall a two-step dance.
- `--generate-hardware-config` is not used; `hosts/emubox/facts.nix` and nixos-hardware are the hardware truth.
- Building: from the Mac, nixos-anywhere builds locally, which means the configured `x86_64-linux` builder. `--build-on remote` is documented as the fallback if no builder is configured; it compiles config files on the N150 and substitutes the rest, so it is slow but correct.
- Secure Boot off, box on Ethernet, booted from the stock NixOS installer ISO with root SSH access enabled (nixos-anywhere connects as `root`; on the stock ISO that means running `sudo passwd` in the live session, or dropping the admin's public key into root's `authorized_keys`). First boot after install: sops decrypts, the WiFi profile is written, `admin` has its password, `player`'s home is created under `/data`.

### D7. VM test: disko's `installTest` on the host config, with test secrets

`checks.x86_64-linux.vm` becomes `(nixosConfigurations.emubox.extendModules { modules = [ ./tests ]; }).config.system.build.installTest`. `tests/default.nix` turns into a NixOS module that carries every test override (sops file and key, `services.openssh.enable`, and the display-manager fallback if it fires) at its own top level and sets `disko.tests.extraChecks` (the Python assertions); `disko.tests.extraConfig` carries nothing and `disko.tests.efi` stays true from systemd-boot. Top level rather than `extraConfig` because disko applies `extraConfig` only inside the harness's internal installed toplevel, whereas a top-level override reaches both the installed system (`installTest` extends the same configuration) and `(nixosConfigurations.emubox.extendModules { modules = [ ./tests ]; }).config.system.build.toplevel`, the only toplevel the flake can name. That expression is the closure root of `checks.x86_64-linux.closure-no-secrets`, the builder-side closure check described below; with overrides in `extraConfig` the check would grep a closure built from `secrets.yaml` and prove nothing. The scaffold's `runNixOSTest` node on `nixosModules.emubox` is replaced; the disko harness runs the actual host config, disko layout included, which is what the spec requires.

- Test secrets contract (this block is the authority; tasks 3.1, 3.2, 3.6, 6.1 and 6.3 derive from it):
  - Key: an SSH ed25519 key pair committed at `tests/test_host_ed25519_key{,.pub}` (`ssh-keygen -t ed25519 -N ""`), labelled as a test key; it protects nothing and the values in the test file are not secrets. An SSH key rather than a bare age key because sops-nix's `sops.age.keyFile` is typed `pathNotInStore`, and anything the test module references is a store path with no non-store home on the installed test system before the users-stage activation; `sops.age.sshKeyPaths` is `listOf path` and accepts store paths, and it is the same ssh-to-age import path the box uses with its real host key.
  - Recipient: `.sops.yaml` gets a creation rule for `secrets/test\.yaml$` whose only recipient is `ssh-to-age < tests/test_host_ed25519_key.pub`. Nothing in it is a recipient of the box's secrets.
  - How it reaches sops-nix: the test module sets `sops.defaultSopsFile = lib.mkForce ../secrets/test.yaml` and `sops.age.sshKeyPaths = lib.mkForce [ ./test_host_ed25519_key ]` (both `mkForce`, because `modules/secrets` defines the same options for the box and plain definitions would conflict or merge the real key path back in), and leaves `sops.age.keyFile` null. The decrypt path is exercised without the real host key.
  - Editing: `test-secrets-edit` (D8) is `SOPS_AGE_KEY=$(ssh-to-age -private-key -i tests/test_host_ed25519_key) sops secrets/test.yaml`, so anyone with a clone can edit the test file.
  - Test values: committed in plaintext at `tests/values.nix` as `{ ssid = "emubox-test"; psk = "emubox-test-psk"; password = "emubox"; hash = "<yescrypt hash of password>"; }`, the hash generated once with `mkpasswd -m yescrypt` when the file is created. They are test-only and not secrets (ruled); the box's real values live only in `secrets/secrets.yaml`. That file is the single source for everything that needs a plaintext test value: `secrets/test.yaml` is encrypted from its values, `extraChecks` imports it for the expected-content assertions and the console login, and the closure check imports it for its grep patterns. Task placement: 1.1 creates the file and wires both importers (so the check has its patterns from the moment it exists), 3.2 encrypts its values, 3.7 and 4.2 assert against it.
- Closure check: the secrets spec's "Secrets never enter the Nix store" scenario is proven builder-side, not from inside the VM. `checks.x86_64-linux.closure-no-secrets` greps every store path listed by `closureInfo { rootPaths = [ (nixosConfigurations.emubox.extendModules { modules = [ ./tests ]; }).config.system.build.toplevel ]; }` for the `psk` and `hash` values imported from `tests/values.nix` and fails if either appears (the `ssid` is not a pattern: it is a substring of the PSK and of test names, and the spec's scenarios name only the PSK and the hash). The patterns are written to a file with `writeText` from `tests/values.nix` and matched with `grep -F -f <that file>`, never interpolated into the script: the yescrypt hash is `$y$j9T$<salt>$<hash>`, and inside a double-quoted `runCommand` script bash would expand `$y`, `$j9T` and `$<salt>` to nothing, leaving grep a fragment that matches nowhere while the check reports green. The red step for the check is planting one of the values in a store path the closure reaches (a throwaway `environment.etc` entry in the test module) and watching it fail. It is not done in the VM because the VM's `/nix/store` is the build sandbox's entire store over 9p (multi-GB, and it contains the test driver script whose Python holds the literal test values), so an in-VM grep both takes far too long and is a guaranteed false positive. In-VM secret assertions are confined to `/run/secrets*` and `/run/NetworkManager`.
- sshd in the VM: no host key is injected, so impermanence's file unit leaves `/etc/ssh/ssh_host_ed25519_key` as a dangling symlink into `/persist/etc/ssh`, a directory nothing creates in the VM; nixpkgs's sshd preStart would run `ssh-keygen -f` through the link and fail, so `sshd.service` would fail on every VM run and look like a regression later. The test module sets `services.openssh.enable = lib.mkForce false`; sshd is loopback-only in this change and nothing asserts on it. On the box the same mechanic is why the install must stage the key: without it sshd generates a fresh key onto `/persist` that is no recipient of the secrets file (README notes this).
- Reboot inside the test: after the harness's booted machine reaches `local-fs.target`, the checks write markers, `machine.shutdown()` then `machine.start()` on the same machine object (the harness's `create_test_machine` result already carries the right disks and OVMF flags), assert, then `machine.crash()` and start again for the power-cut scenario. `machine.reboot()` is avoided because the driver runs QEMU with `-no-reboot`.
- Assertions map one-to-one to the `vm-test` spec: subvolume mounts, boot through the loader (the "Current Boot Loader" block of `bootctl status` names systemd-boot; the "Available Boot Loaders" block would list it even after a direct kernel load), every persisted directory and file resolving under `/persist`, the four persistence assertions plus the power-cut survival of `/data` and the machine-id, `/tmp` clean, `/run` on tmpfs, a `Persistent=true` timer stamp keeping its mtime across the reboot, secrets present with mode and content (expected content is compared in Python, `machine.succeed("cat <path>").strip() == value` with the value imported from `tests/values.nix`, never passed through the guest shell, so the in-VM checks follow the same no-interpolation rule as the closure check; a guest-side `grep` would expand the yescrypt hash's `$` fragments and match vacuously), admin console login on tty1 via `wait_until_tty_matches` with explicit timeouts (the display manager is off in the test, see below, so tty1 carries a getty), `nmcli connection show family-wifi` and PSK in the generated file (waiting on the rendered file and the oneshot's `Result`, since `NetworkManager-ensure-profiles.service` has no `RemainAfterExit` and `wait_for_unit` on it would raise), listeners loopback-only, WirePlumber fragment installed, hygiene timers active, the watchdog declaration in `system.conf` (the live `RuntimeWatchdogUSec` needs a watchdog device the VM lacks; hardware checks it). Guest commands never use a shell pipe: the driver runs them under `pipefail`, and a `grep -q` closing the pipe early would fail the producer with SIGPIPE.
- Cost: four VM boots per run (the installer, then the installed system three times: initial, after `shutdown()`, after `crash()`) plus the install itself, inside the driver's 3600 s global timeout. KVM and the 9p store bind keep it in minutes.
- Harness limits: disko's `create_test_machine` starts the booted VM with a hard-coded `-m 1024` and exposes no memory knob (`disko.tests.extraConfig` is NixOS configuration for the installed system, not VM settings; `virtualisation.memorySize` is not a defined option there because qemu-vm.nix is not imported). Its `meta.timeout = 600` is a Hydra hint that `nix build` ignores; the bound that applies is the test driver's default `globalTimeout` of 3600 s. The host config carries Plasma, so 1 GB is the budget the test has to fit in. The test module sets no memory option. The display-manager fallback from Risks is applied by decision rather than by measurement (no KVM builder was available to measure the memory budget): `services.displayManager.sddm.enable = lib.mkForce false` at the test module's top level, so the graphical stack is neither started nor waited on and the console login is on tty1's getty, a VT the kiosk session cannot own (with SDDM on, its VT is chosen at runtime and tty1 carries no getty, so a tty2 login would race the compositor). The graphical session is proven on hardware (E12).

### D8. Files and recipes

- `justfile`: `secrets-edit` (`sops secrets/secrets.yaml`), `secrets-rekey` (`sops updatekeys secrets/secrets.yaml`), `test-secrets-edit` (`SOPS_AGE_KEY=$(ssh-to-age -private-key -i tests/test_host_ed25519_key) sops secrets/test.yaml`), `host-key <path>` (generate if absent), `install <target> [host-key]`.
- Deploy contract: within this change the only remote path to the box is the nixos-anywhere install (D6). sshd listens on loopback only, root login is refused and no admin authorized key is declared, so the networking spec's "nothing listens on the LAN" holds as written and there is no address a `nixos-rebuild --target-host` could reach. Push deploy arrives with E10, which makes the box reachable over the tunnel and owns the `deploy` recipe, its default target and its post-install check; the expected shape is `nixos-rebuild switch --flake .#emubox --target-host` (the `nixos-rebuild-ng` already in the devShell) as `admin` with `--sudo`, but that is E10's decision to confirm. Until E10, a changed configuration reaches the box by reinstall (D6, `/data` restored from backup) or by hand at the recovery desktop (`admin` clones the repo and runs `nixos-rebuild switch --flake` locally; `wheelNeedsPassword` is already off); neither is a documented recipe here. Why not colmena or deploy-rs when E10 comes: both are fleet tools, and for one host they add a configuration layer and a dependency without adding capability; deploy-rs's magic rollback is superseded by E11's boot assessment, which also covers the unattended auto-update path. If a second host ever exists, colmena is the candidate and `nixosModules.emubox` is already the shareable unit.
- `README.md` install section becomes the runbook (prerequisites, host key, secrets, command, post-install checklist, reinstall/disk swap, and a note that push deploy is E10's). `secrets/README.md` lists the keys and both files with their recipients.

## Risks / Trade-offs

- [Rollback unit ordering wrong, root mounts before the wipe or the unit waits on a device that never appears and the boot hangs] → The VM test goes through the same initrd; `requiredBy = sysroot.mount` makes a wipe that fails a visible boot failure, not a silent no-op, and `ConditionPathIsMountPoint=!/sysroot` makes a wipe that would run against a mounted root a skipped unit, caught by the persistence assertions (D1). Partition label and initrd PATH are verified in the VM before the unit is trusted.
- [`btrfs` not on the initrd PATH] → Verified in the VM; fallback is `boot.initrd.systemd.extraBin.btrfs`.
- [machine-id or host key not present when sops runs on the very first boot after install] → Host key is injected by the install; machine-id is bound to `/persist` by the initrd unit from D2 and initialises in place on the first boot. First-boot behaviour is exactly what the installTest exercises.
- [The disko harness's fixed 1 GB VM memory proves short for a host config that carries Plasma, on the CI runner] → Applied up front (D7): the test module `mkForce`s the display manager off at its top level (`services.displayManager.sddm.enable = false`, not in `extraConfig`) so the graphical stack is neither started nor waited on; the initrd, persistence, secrets and networking paths are unaffected and the admin console login is on a plain getty. The graphical session is proven on hardware (E12), as it is today.
- [disko installTest is heavier and less familiar than a plain test node] → Accepted: it is the only route that tests the real layout without re-implementing disko's harness. Later epics add assertions to `extraChecks`; nothing forces them back to a plain node.
- [Secrets in `/run/secrets-for-users` are root-readable only; the password hash is fine there] → No consumer other than user creation.
- [`node.restore-default-targets = false` also stops a deliberate `wpctl set-default` from sticking] → Intended on a kiosk; the recovery desktop is a session, not a place to keep audio state.
- [Journal cap loses history on a chatty failure] → 256 MB at this box's rate is weeks; the cap protects the disk, which matters more.
- [The "missing persistent volume stops the boot" scenario is not exercised in the VM] → It is `neededForBoot` semantics, which the same initrd path enforces: a failed `neededForBoot` mount fails `initrd-fs.target` and the systemd initrd enters emergency mode, which is what the spec promises and no more (no rescue prompt is promised; `boot.initrd.systemd.emergencyAccess` is not set, so the emergency shell is not reachable without a password). Breaking a disk in the harness is not worth a test. Recorded in tasks as a documented, not tested, guarantee.
- [A secret fails to decrypt on the box (host key does not match a recipient, or a key is missing from the file)] → The failure is visible and the boot still reaches a console: the users-stage `sops-install-secrets` logs the failing secret to the journal and activation continues; a missing `hashedPasswordFile` leaves `admin` without a usable password rather than blocking user creation, and a getty is still reached; the `NetworkManager-ensure-profiles` unit fails on the missing env file without taking NetworkManager itself down. This is the behaviour the secrets spec's "Decryption failure is visible" scenario promises; it is design-guaranteed, not asserted by the VM test.
- [Admin loses the age key or host key] → Both are documented as backed-up admin artefacts; losing the age key means re-creating the secrets file from the admin's own knowledge, losing the host key means one re-key. Neither loses family data.

## Migration Plan

Nothing is deployed yet; there is no live box to migrate. Landing order inside the change: rollback unit and persistence first (the VM test's core), then secrets and the test key, then WiFi and base-system leftovers, then the runbook and recipes. Each step keeps `just check-all` green on the Mac, where `nix flake check` skips the `x86_64-linux` checks; CI, which runs them, is red from the persistence assertions (task 1.3) until the rollback lands (task 2.4), which is the intended TDD arc. The repository has no remote while the change is built; the first CI run is the change's first VM-test run and happens on a pull request from the change branch (the workflow triggers on `push` to `main` and on `pull_request`), after the local pre-flight from Context is green. First-run items to watch in the job log: the udev step actually changes `/dev/kvm`'s mode (a run that reaches the driver's 3600 s timeout means it did not), the runner's disk holds the host closure plus the test's disk images, and the whole job fits the default 6 h job limit. Rollback strategy is git: the change is a branch off `main`.
